# 블로그 자동 발행 파이프라인 (발췌본)

AI가 쓴 글을 사람이 매번 읽지 않고도 내보낼 수 있으려면 무엇이 필요한가. 이 질문에서 시작한 개인 프로젝트의 일부다. 글감 정리, 초안, 규칙 검사, 수정, 발행, 색인 요청까지를 코드로 묶은 파이프라인으로, 2026년 7월 중순부터 약 4주 동안 네이버·티스토리 두 블로그에 합쳐 약 300편을 자동 발행했다(두 블로그의 글을 합친 수이고, 이후 일부 글은 삭제했다). 지금은 돌리지 않는다.

혼자 만들었고 AI 코딩 도구를 함께 썼다.

이 저장소는 그중 판단·검사·스케줄 코드 여섯 파일을 2026-09-03에 떼어 낸 것이다. 위 발행 기간(7~8월)보다 뒤의 코드라, 9월 1~2일 무한 루프 사고(호출이 하루 4천~7천 회까지 늘어남) 뒤에 고친 모습이 담겨 있다. 발행 기간의 코드와 같지 않다.

## 들어 있는 것과 뺀 것

- 들어 있는 것: `src/` 아래 여섯 파일(아래 표).
- 뺀 것: 네이버·티스토리 발행 스크립트, 그 스크립트와 `gsc_index.py`가 쓰는 브라우저 제어 모듈(`cdp`), 초안 생성 코드와 프롬프트(`draft.py`), 각 라인이 실제로 실행하는 스크립트(`run.py` 등), 비밀값·계정 정보, 운영 데이터(`state/`, `drafts/`). 발행은 로그인된 브라우저를 조작하는 방식이라 계정 보호를 위해 올리지 않았다.
- 코드 안의 `<TISTORY_ID>`, `<EMAIL>`, `<DISCORD_DM_CHANNEL_ID>` 같은 꺾쇠 표기와 `~` 경로는 공개하면서 바꿔 넣은 자리 표시다.

## 파일별로 볼 곳

| 파일 | 보여 주는 것 | 볼 함수·값 |
|---|---|---|
| `src/verify.py` | LLM을 쓰지 않는 규칙 검사 8종(고칠 대상 6, 기록만 2). 걸린 것이 있을 때만 수정 호출 1회, 수정본이 원문의 60% 미만이면 버림, 조사 단계에서 모은 URL만 쓰게 함 | `code_checks`, `verify_and_fix`, `MIN_KEEP_RATIO`, `_materials`, `REVISE_PROMPT` |
| `src/llm.py` | 하루 자동 호출 상한, 한도 오류일 때만 다음 모델로 넘기기, 호출자·모델별 호출 수와 비용 기록 | `_capped`, `DAILY_CAP`, `_ask_chain`, `_log_usage` |
| `src/company.py` | 상주 루프 없이 한 번 돌고 끝나는 스케줄러. 시도를 먼저 기록, 실행 전 자체 점검, 발행 URL 생존 확인, 연속 실패 시 재시도 간격 2·4·8·16·24시간, 정상 코드 스냅샷과 롤백 | `run_line`, `_skip_reason`, `BACKOFF_H`, `_snapshot`, `_rollback`, `_heal`, `report`, `selftest` |
| `src/enrich.py` | X 좋아요에 달린 외부 링크를 풀어 요약해 글감으로 쌓음. 내부 주소 요청 차단, 외부 페이지 내용을 지시로 따르지 않게 하는 프롬프트 | `guard`, `_ValidatingRedirect`, `summarize`, `FENCE` |

## 숫자

- 편수: 위 약 300편. 발행 기록 파일에서 URL이 적힌 것을 같은 URL은 한 번만 세어 낸 값이다(08-11까지 288, 08-12까지 309).
- 글 한 편의 LLM 호출: 이 발췌본에서 코드로 보이는 것은 수정 호출 최대 1회(`verify.py` 244~250행)다. 초안 1회를 더해 최대 2회라는 것은 주석(237~238행)에만 있다. 원래 파이프라인은 2026년 9월 초 기준 글 한 편에 8~12회를 썼다.
- 하루 호출 상한: 2026년 9월 1~2일 같은 작업이 끝없이 다시 실행돼 호출이 하루 4천~7천 회까지 늘어난 무한 루프 사고 뒤에 넣었다. 처음 3회로 잡았다가 글 한 편도 못 쓰는 값이라 15회로 올렸다(`llm.py` 132~134행, 기본값 15). 남은 호출 수가 그 라인에 필요한 수보다 적으면 LLM을 쓰는 라인은 건너뛰고, LLM을 쓰지 않는 감시 라인은 그대로 돈다(`company.py` 230~233행).
- 광고 수입은 2026년 9월 초까지 0원이었다. 방문자·매출·시간 절감은 성과로 적지 않는다.

## 설계에서 정한 것

- 검사는 발행을 막지 않는다. `verify_and_fix`는 발행하지 않고, 고친 뒤에도 남은 지적(`remaining`)만 돌려준다. 최종 발행 판단 코드는 이 발췌본에 없다.
- 제동은 여러 겹이다. 하루 호출 상한, 라인별 하루 실행 횟수(`max_per_day`), 연속 실패 시 재시도 간격(`BACKOFF_H`), 한 번에 요약할 링크 수(`ENRICH_MAX`, 기본 2).
- 롤백은 새 코드를 쓰지 않고 마지막으로 정상 종료한 코드를 되살린다. 실행 전 점검이 실패하거나 3번 연속 실패하면 동작한다. 이 발췌본에서 롤백 대상 폴더(`dir`)가 있는 라인은 하나뿐이고, 나머지 라인과 롤백 뒤에도 실패하는 라인은 안건으로 올리고 메신저로 알린다.

## 확인한 것과 못 한 것

- 이 저장소만으로 돌아가는 점검(2026-11-11, 작성자 맥에서 저장소 루트 기준으로 실행):
  - `python3 src/cats.py` → `ok`
  - `python3 src/company.py --selftest` → `selftest OK`. `/opt/homebrew/bin/python3`이 있어야 하고, 실행하면 루트에 빈 `state/` 폴더가 생긴다.
  - `python3 -c "import sys; sys.path.insert(0, 'src'); import llm; llm._check()"` → `check ok`
  - `python3 -c "import sys; sys.path.insert(0, 'src'); import verify; print(verify.code_checks('## 정리\n그냥 본문'))"` → 고칠 대상 6개, 기록만 2개
- 돌아가지 않는 것: `python3 src/verify.py --check`는 운영 데이터(`drafts/` 아래 글)가 없어 실패한다. `gsc_index.py`는 `cdp` 모듈이 없어 불러올 수 없다. 실제 실행 경로(발행, LLM 호출, 색인 요청)는 빠진 파일과 계정이 있어야 해서 이 저장소로는 재현되지 않는다. 읽기용 발췌본이다.
- 안정판 판정은 종료 코드 0만 본다. 글 품질이 나빠진 버전도 정상 종료하면 안정판이 된다(`company.py` 19행).
- 규칙 검사 8종은 내 블로그 글에 맞춘 것이다. 다른 종류의 글이나 일에 통하는지는 확인하지 않았다.

## 읽을 때 주의

- `verify.py` 맨 위 설명(1~15행)은 이전 설계(LLM 채점 후 수정 반복, 최대 5회 호출)를 적고 있다. 지금 동작은 26행과 237~238행 주석, `verify_and_fix` 본문이 맞다. `CRITIQUE_PROMPT`, `_parse_critique`는 남아 있지만 쓰이지 않는다.
- `enrich.py` 설명은 요약에 Gemini를 쓴다고 적지만 코드는 Claude 모델을 부른다(145~151행).
- 주석에 나오는 "유저"는 작성자 본인을 가리킨다.
- `llm.py` 351행 주석은 사고 당일의 추정을 적은 것이다. 이후 추적에서 원인은 재실행 루프와 재시도 판정이었고, 무료 대체 경로는 설정 누락과 오류로 동작하지 않아 호출이 한 경로로 몰린 것으로 확인했다.
